TASK DEFINITION – DIALOGUE INTENT CLASSIFICATION (8 CLASSES)

Challenge: Single-label classification of a user's intent from a short
Russian-language dialogue for the assistant of the fictional "Meridian"
platform (company "Arcadia"). The classifier must look at the current
message together with the visible history and pick one of eight routing
branches. The same short phrase in different dialogues can mean different
intents.

OBJECTIVE
Implement `def entrypoint():` (no arguments) that returns a dict mapping
example id -> prediction:
    {
        "<example_id>": {"intent": <label>, "needs_clarification": <bool>},
        ...
    }

Requirements:
1) `intent` is one of 8 labels:
     greeting, capabilities, gratitude, data_catalog,
     pivot_table, technical, support, no_rag
2) `needs_clarification` is a boolean flag, allowed to be True ONLY when
   `intent == "data_catalog"`. It marks genuine ambiguity between
   "find catalog objects" and "explain a topic".
3) Predictions must be produced ONLY from each example's `history` and
   `text`. Fields `intent`, `needs_clarification`, `rationale`, `tags`,
   `group_id`, `split` are forbidden as model input.
4) `history` is a chronological list of {"role": "user"|"assistant",
   "content": str}. The current user message is in `text` and is NOT
   duplicated in `history`. Up to 3 previous user and 4 previous
   assistant turns. Empty history is valid.
5) Deterministic: no randomness, or seed it if you must.

Output type: dict[str, dict]. No printing, no side effects, no I/O.


DATA ACCESS — READ THIS FIRST
All 160 examples are ALREADY embedded in `helper.py` as a Python string
variable named `EMBEDDED_EXAMPLES` (JSONL form: one JSON object per line).
Every example in that string contains ONLY these fields:
    id, history, text

It does NOT contain gold fields (`intent`, `needs_clarification`) and
does NOT contain `rationale`, `tags`, `group_id`, `split`. This is
intentional — predictions must come from `history` + `text` alone.

RULES:
- DO NOT open, read, or look for `examples.json` at runtime.
  It does not exist in the sandbox.
- DO NOT use `open()`, `json.load()`, `pd.read_json()`, `Path.read_text()`
  or any other file I/O on examples. Everything is already in memory.
- DO NOT try to reconstruct gold labels. Gold is stored by the judge
  outside the sandbox; the program cannot see it and must not want to.
- Use `helper.load_examples()` to get the list of examples, or parse
  `helper.EMBEDDED_EXAMPLES` directly. Both give the same result.
- `entrypoint()` must iterate over `helper.load_examples()` and return
  {id: {"intent": ..., "needs_clarification": ...}}.

Available helpers in `helper.py`:
- `LABELS`                  -> list of the 8 valid intent names
- `EMBEDDED_EXAMPLES`       -> str, all 160 examples (id, history, text)
- `load_examples()`         -> list[dict] parsed from EMBEDDED_EXAMPLES
- `last_assistant(history)` -> str, last assistant turn, lowercased

Validation reads gold from its own copy of `examples.json` (outside the
sandbox). The mutating program must never attempt to access it.


FITNESS AND VALIDITY
Fitness = macro-F1 over the 8 intent classes. Each class weighs equally.
Higher is better. Range [0.0, 1.0].

is_valid = 1 when every prediction is structurally correct:
- `intent` is one of the 8 labels,
- `needs_clarification` is a bool and True only for `data_catalog`.
Otherwise is_valid = 0.

A wrong `intent` still counts as a valid prediction — it just lowers
fitness. InvalId is reserved for malformed output, not for mistakes.


DATASET
- 160 synthetic hand-labeled examples, 20 per class.
- 16 train / 4 dev per class (128 train, 32 dev).
- Same phrase with different histories forms minimal pairs (shared
  `group_id`), never split across train/dev.
- Only synthetic data; no real user logs were used.
- `split` is not available inside the sandbox and must not be used.


THE EIGHT INTENTS
- greeting          — hello or standalone neutral farewell, no work task.
- capabilities      — question about the assistant itself, its identity
                      or its abilities.
- gratitude         — thanks, confirmation that help is finished,
                      "no further questions".
- data_catalog      — find tables, marts, cubes, dashboards, views, or
                      any data object; continue a catalog listing.
- pivot_table       — explicit request to build or edit a numeric table
                      with dimensions, filters, or aggregation.
- technical         — explanations, methodology, errors, access, product
                      questions; the default class.
- support           — explicit request for a human operator, or an
                      unambiguous choice of the operator option from the
                      assistant's last menu.
- no_rag            — operation on the visible history: repeat, shorten,
                      translate, reformat the already-provided answer,
                      or ask about the dialogue itself.


ANNOTATION CONVENTIONS
- Standalone "пока" / "до свидания" -> greeting; "вопросов больше нет",
  "на этом всё" -> gratitude.
- Polite opening ("Привет, ...", "Спасибо, а ...") does NOT override an
  explicit work task in the same message.
- On doubt between support/technical, pivot_table/technical, or
  no_rag/technical -> choose technical.
- On doubt between data_catalog and an explanation -> data_catalog with
  `needs_clarification = true`.
- "Оформи это таблицей" -> no_rag if the previous assistant answer
  already contains all needed facts, otherwise pivot_table.
- A negative form flips the intent: "не зови оператора, объясни ..."
  -> technical; "Специалиста не подключайте" -> technical.


CONTEXTUAL MINIMAL PAIRS (the same text, different history)
- "Покажи ещё" after a catalog listing -> data_catalog
- "Покажи ещё" after a topic offer     -> technical
- "Вариант 2" after a menu with operator -> support
- "Вариант 2" after a menu with explanations -> technical
- "Оформи это таблицей" when the facts are already in history -> no_rag
- "Оформи это таблицей" when only a future pivot was agreed -> pivot_table
- "Когда она начинает действовать?" after an explicit date -> no_rag
- "Когда она начинает действовать?" after a bare method name -> technical
- "А за июль?" after a pivot for August -> pivot_table (new numbers needed)


FAILURE MODES
- Treating a short phrase as a keyword while ignoring context.
- Confusing capabilities (about the assistant) with technical (about the
  platform "Меридиан" or a product).
- Confusing data_catalog (find sources) with pivot_table (build numbers),
  or with technical (explain a metric).
- False no_rag when the required fact is not in the visible history.
- False support when the user only asked a technical question, or when
  the word "оператор" appears inside a negation.
- Short greetings like "пока" matching inside "пока таблицу" — check
  word boundaries, not raw substrings.


IMPLEMENTATION GUIDANCE
- A simple keyword baseline is a perfectly acceptable starting point.
- Prefer plain Python: lists of substrings, `re`, `str.lower()`.
- Only `helper.py` may import from outside stdlib if necessary.
- Keep the code short and readable — mutations should be able to change
  small pieces without breaking the whole file.
- The typical weak baseline uses a dictionary of keyword lists per class
  plus a small context resolver for the minimal pairs above.
- Return `{"intent": "technical", "needs_clarification": False}` when
  no rule fires — `technical` is the default class.
- `entrypoint()` must not take arguments. It reads examples itself via
  `helper.load_examples()` and returns the full prediction dict.


OUTPUT FORMAT

Implement `def entrypoint():` with NO arguments that:
- Calls `helper.load_examples()` to get the examples.
- Uses ONLY `history` and `text` from each example.
- Returns a dict: {example_id: {"intent": <label>,
                               "needs_clarification": <bool>}}.
- Uses only the standard library (plus numpy/scipy/re if needed).
- Does not touch the filesystem at runtime.
- Return type: dict[str, dict].

NEGATIONS CHANGE THE INTENT
--------------------------------------------------
"Позови оператора."                       -> support
"Не зови оператора, объясни ошибку."      -> technical
"Специалиста не подключайте. Что делать...?" -> technical
"Нет, спасибо."                           -> gratitude
--------------------------------------------------

POLITE OPENING DOES NOT OVERRIDE THE TASK
--------------------------------------------------
"Привет!"                                       -> greeting
"Привет, почему не открывается отчёт Мозаики?" -> technical
"Спасибо!"                                      -> gratitude
"Спасибо, а сколько хранятся сообщения?"        -> technical
