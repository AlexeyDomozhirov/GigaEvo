TASK DEFINITION – DIALOGUE INTENT CLASSIFICATION (8 CLASSES)
============================================================================

Challenge: Single-label classification of a user's intent from a short
Russian-language dialogue for the assistant of the fictional "Meridian"
platform (company "Arcadia"). The classifier must look at the current
message together with the visible history and pick one of eight routing
branches. The same short phrase in different dialogues can mean different
intents.

This is a long-running evolution. Your mutation should make the program
slightly better. Read this whole document before editing.

OBJECTIVE
Implement `def entrypoint():` (no arguments) that returns a dict mapping
example id -> prediction:
    {
        "<example_id>": {"intent": <label>, "needs_clarification": <bool>},
        ...
    }

CONTRACT (must not break):
1) `intent` is one of 8 labels:
     greeting, capabilities, gratitude, data_catalog,
     pivot_table, technical, support, no_rag
2) `needs_clarification` is a boolean flag, allowed to be True ONLY when
   `intent == "data_catalog"`. It marks genuine ambiguity between
   "find catalog objects" and "explain a topic".
3) Predictions must be produced ONLY from each example's `history` and
   `text`. Fields `intent`, `needs_clarification`, `rationale`, `tags`,
   `group_id`, `split` are forbidden as model input.
4) `history` is a chronological list of {"role": "user"|"assistant",
   "content": str}. The current user message is in `text` and is NOT
   duplicated in `history`. Up to 3 previous user and 4 previous
   assistant turns. Empty history is valid.
5) Set `temperature=0.0` for reproducibility. Some residual
   non-determinism may remain — the LLM API does not guarantee
   byte-identical outputs. Do not rely on exact repetition.
6) `entrypoint()` takes no arguments. It reads examples itself via
   `helper.load_examples()`.
7) Credentials come from the environment variable `GIGACHAT_CREDENTIALS`.
   Do NOT print it, log it, pass it into the prompt, or hardcode it in
   the file. Do NOT read it from disk.
8) On any API or parse error, fall back to
   {"intent": "technical", "needs_clarification": false}.
   Never raise, never print, never skip an id.

Output type: dict[str, dict]. No printing, no side effects, no file I/O.

FITNESS: macro-F1 over the 8 classes. Each class weighs equally.
Higher is better. Range [0, 1].

is_valid = 1 when every prediction is structurally correct:
- `intent` is one of the 8 labels,
- `needs_clarification` is a bool and True only for `data_catalog`.
Otherwise is_valid = 0.

A wrong `intent` still counts as a valid prediction — it just lowers
fitness. Invalid is reserved for malformed output, not for mistakes.

WHAT KIND OF PROGRAM YOU MUTATE
============================================================================
The program you receive is a Python wrapper around a GigaChat LLM call.
Almost all classification quality comes from the TEXT of the SYSTEM
prompt, not from the Python logic.

Typical structure of such a program:
  - imports (langchain-gigachat, langchain-core, pydantic, helper)
  - a SYSTEM constant — the big Russian-language prompt
  - a chain that sends SYSTEM + user message to GigaChat
  - a parser that extracts {intent, needs_clarification} from the reply
  - a `_normalize()` or similar function that validates the output
  - `_predict_one(history, text)` — one API call
  - `entrypoint()` — loops over examples

The model (GigaChat) ALREADY KNOWS Russian, ALREADY understands what
"привет", "спасибо", "оператор", "сводная" mean. You do NOT need to
teach it vocabulary. You need to clarify AMBIGUOUS cases and MINIMAL
PAIRS where context decides the class.

Your main mutation surface is the SYSTEM prompt:
  - class descriptions
  - conventions and rules
  - few-shot examples
  - output format instructions

MUTATION POLICY — READ BEFORE EDITING
============================================================================

You are the mutation operator. You receive the current best program and
this document. Your job is to make ONE THEMATIC improvement.

RULES:

1) ONE THEME PER MUTATION — NOT ONE LINE.
   A "theme" is one failure mode you are fixing. Within that theme you
   may make several related additions at once, because each mutation
   costs 160 LLM calls to evaluate — small changes do not pay off.

   GOOD thematic changes (each counts as ONE mutation):
     - Fix context pairs end-to-end: add a short rule sentence about
       "same text, different history" AND 3–4 few-shot examples for
       the most confused pairs (Вариант 2, Покажи ещё, Оформи таблицей).
     - Fix negation handling: add one rule sentence about negations
       AND 2–3 few-shot examples for the "не зови оператора" family.
     - Strengthen output format: rewrite the format section to strict
       JSON AND add 1 example AND forbid markdown explicitly.
     - Clarify a class boundary: add a 3–5 line block distinguishing
       capabilities / technical / data_catalog AND 1–2 paired
       few-shot examples.
     - Add a decision tree for pivot_table vs data_catalog vs technical
       in one block.

   BAD "mutations" (still not allowed):
     - Rewrite the whole SYSTEM prompt.
     - Mix 3+ unrelated themes in one mutation (e.g. add examples for
       greeting AND support AND no_rag at once). 3–4 examples for ONE
       theme are fine and encouraged.
     - Change Python logic AND the prompt in one mutation.
     - Mix "fix format" and "fix negation" in one mutation.

   Rule of thumb: if you cannot describe the change in one sentence
   of the form "I am fixing X by doing Y", it is more than one theme.

2) DO NOT TOUCH THE PYTHON LOGIC.
   Keep imports, API calls, parsing, `_predict_one`, `entrypoint`,
   `_normalize` as they are. If a Python change is truly necessary,
   change one line and comment why. In 95% of mutations, only the
   SYSTEM prompt text changes.

3) DO NOT REWRITE THE PROMPT FROM SCRATCH.
   Keep its sections: task definition, class list, conventions,
   format rules, few-shot examples. Add to existing sections or
   extend them. Do not restructure.

4) LEVERAGE THE MODEL'S KNOWLEDGE.
   Do NOT add vocabulary rules like "если слово привет то greeting".
   GigaChat already knows what "привет" means. Add rules for
   AMBIGUOUS cases only:
     Good: "Вопрос «Ты умеешь искать витрины?» — capabilities,
            потому что спрашивают о способности ассистента."
     Bad:  "Слово витрин → data_catalog"

5) NEVER HARDCODE a specific `text` -> `intent` mapping in the Python.
   Bad:  if text == "Привет!": return "greeting"
   Good: add a few-shot example for greeting to the SYSTEM prompt.

6) PREFER GENERALISATION.
   Few-shot examples must be REPRESENTATIVE of a class, not exact
   test strings. Show patterns, not memorised lines.

7) IF NO CLEAR THEME IS AVAILABLE, RETURN THE FILE UNCHANGED.
   Each evaluation costs 160 GigaChat API calls. Do not waste them on
   guesses. A no-op is better than a risky rewrite.

8) DO NOT ADD EXTERNAL DEPENDENCIES.
   Allowed imports: `langchain-gigachat`, `langchain-core`, `pydantic`,
   `helper`, and `os` (only for reading `GIGACHAT_CREDENTIALS`).
   Do NOT import `re`, `json`, `numpy`, `sklearn`, `torch`, or anything
   else. The LLM parser already handles JSON extraction — do not add
   regex post-processing.

9) DO NOT USE FILESYSTEM AT RUNTIME.
   `examples.json` does not exist in the sandbox. Use
   `helper.load_examples()` only.

10) KEEP THE SYSTEM PROMPT UNDER ~180 LINES.
    The mutation budget is bigger than "one line", but do not bloat.
    Shorter prompts are faster and cheaper per call.

============================================================================
ANNOTATION CONVENTIONS
============================================================================

1) FAREWELL vs GRATITUDE
   Standalone "пока" / "до свидания" -> greeting
   "вопросов больше нет", "на этом всё", "мне всё ясно" -> gratitude
   Mixed ambiguous farewells are excluded from the dataset.

2) POLITE OPENING DOES NOT OVERRIDE A TASK
   "Привет, почему не открывается отчёт?" -> technical
   "Спасибо, а сколько хранятся сообщения?" -> technical
   If a greeting or thanks word co-occurs with a work marker
   (почему / как / что такое / найди / покажи / построй / ошибка /
   методика / срок / регламент / расскажи / объясни), return the work
   class, not greeting/gratitude.

3) ON DOUBT — CHOOSE technical
   Support vs technical -> technical
   pivot_table vs technical -> technical
   no_rag vs technical -> technical
   False support triggers an unnecessary human handoff.
   False no_rag skips knowledge search and answers without facts.
   Both are worse than a false technical (which just does extra search).

4) CATALOG vs EXPLANATION AMBIGUITY
   If unclear whether the user wants catalog objects or an explanation:
   -> data_catalog with needs_clarification = true

5) "Оформи это таблицей"
   If the previous assistant answer already contains all needed facts
   -> no_rag
   If only a future pivot was agreed (no numbers yet)
   -> pivot_table

============================================================================
NEGATIONS — a negative form flips the intent
============================================================================
"Позови оператора."                                  -> support
"Не зови оператора, объясни ошибку."                 -> technical
"Специалиста не подключайте. Что делать ...?"        -> technical
"Не повторяй инструкцию, лучше позови оператора."     -> support
"Нет, спасибо."                                      -> gratitude
"Не объясняй формулу, просто найди витрину."         -> data_catalog
"Не строй пока таблицу. Скажи, умеешь ли ты это?"    -> capabilities

Rule: if "не" appears in the same clause as an operator/specialist
word AND the request is to EXPLAIN, the intent is technical. If the
negation is about something ELSE ("не повторяй инструкцию, лучше
позови") — the intent stays support.


============================================================================
POLITE OPENINGS — task wins over greeting/thanks
============================================================================
"Привет!"                                       -> greeting
"Привет, почему не открывается отчёт Мозаики?"  -> technical
"Спасибо!"                                      -> gratitude
"Спасибо, а сколько хранятся сообщения?"        -> technical
"Здравствуйте, помогите разобраться с ошибкой." -> technical


============================================================================
GOOD MUTATION EXAMPLES (for an LLM-based program)
============================================================================
Each example below is a FULL thematic change — the kind that pays off
within one evaluation. Notice that each includes a rule AND examples.

Example A — Fix context pairs end-to-end (priority 1):
  Add to SYSTEM:
    "Одна и та же короткая фраза может означать разные интенты в
     зависимости от последней реплики ассистента. Всегда смотри на
     историю перед выбором intent."

  Add three few-shot pairs:
    История: A: Выберите: вариант 1 — автопроверка; вариант 2 — оператор.
    Сообщение: Вариант 2.
    Ответ: {"intent": "support", "needs_clarification": false}

    История: A: Могу дать: вариант 1 — краткое; вариант 2 — подробное.
    Сообщение: Вариант 2.
    Ответ: {"intent": "technical", "needs_clarification": false}

    История: A: Найдены PrismDaily и PrismDeals. Есть ещё объекты каталога.
    Сообщение: Покажи ещё.
    Ответ: {"intent": "data_catalog", "needs_clarification": false}

    История: A: Мы обсудили порог. Могу показать обработку возвратов.
    Сообщение: Покажи ещё.
    Ответ: {"intent": "technical", "needs_clarification": false}
  Reason: the context-pair family is the biggest source of errors.
  One coherent fix covers several top confusions at once.

Example B — Fix negation handling end-to-end (priority 2):
  Add to SYSTEM:
    "Отрицание меняет интент. Если пользователь говорит «не зови
     оператора, объясни ...» — это technical. Если отрицание
     относится к чему-то другому («не повторяй инструкцию, лучше
     позови оператора») — это support."

  Add two few-shot examples:
    Сообщение: Не зови оператора, объясни ошибку CHECKSUM_MISMATCH.
    Ответ: {"intent": "technical", "needs_clarification": false}

    Сообщение: Не повторяй инструкцию, лучше позови оператора.
    Ответ: {"intent": "support", "needs_clarification": false}
  Reason: negation errors cost both fitness and is_valid.

Example C — Clarify a class boundary (priority 4):
  Add to SYSTEM a short block:
    "Различай:
     - capabilities: вопрос о возможностях ассистента
       («Что ты умеешь?», «Ты умеешь искать витрины?»)
     - technical: вопрос о платформе или продукте
       («Что такое платформа Меридиан?», «Что ты знаешь о Призме?»)
     Если пользователь спрашивает о СПОСОБНОСТИ ассистента — это
     capabilities, даже если упоминается объект данных."

  Add one paired example showing the boundary.
  Reason: capabilities ↔ technical is a common confusion.

Example D — Strengthen output format (priority 8):
  Replace the format line in SYSTEM with a strict block:
    "Ответ — СТРОГО ОДНА строка валидного JSON. Без markdown, без
     ```json, без текста до или после.
     Формат: {"intent": "<label>", "needs_clarification": <bool>}"
  Reason: improves `is_valid` and reduces parser fallbacks.

Example E — Tighten needs_clarification (priority 7):
  Add to SYSTEM:
    "needs_clarification=true ТОЛЬКО для data_catalog и ТОЛЬКО
     если запрос можно понять и как поиск объекта, и как объяснение
     темы. Во всех остальных случаях — false."
  Add one example with needs_clarification=true and one counterexample
  with false.
  Reason: is_valid depends on this flag being correct.


============================================================================
BAD MUTATION EXAMPLES
============================================================================
These HURT fitness or waste evaluations.

Bad A — rewrite the whole SYSTEM prompt from scratch.
Bad B — mix 3+ unrelated themes in one mutation (e.g. add examples for
        greeting AND support AND no_rag at once). 3–4 examples for ONE
        theme are fine and encouraged.
Bad C — change the API call or parser logic.
Bad D — add rules like "if слово привет → greeting" (GigaChat knows).
Bad E — hardcode test strings as rules.
Bad F — add sklearn, embeddings, or any other API.
Bad G — read `examples.json` from disk.
Bad H — set `temperature` above 0.2 (non-determinism hurts).
Bad I — turn the LLM program into a regex program or vice versa.
Bad J — add `re` or `json` imports to post-process the LLM reply;
        the parser already handles JSON extraction.


============================================================================
IMPLEMENTATION GUIDANCE
============================================================================
- The SYSTEM prompt is your main mutation surface.
- Few-shot examples go inside the SYSTEM prompt, not in the human
  message template. Keep them stable.
- Place each new few-shot example LAST among examples for its class
  (recency matters for LLMs).
- `_normalize()` and `_fallback()` are safety nets. Leave them as
  they are; they protect `is_valid` from model hallucinations
  (e.g. class "farewell" not in LABELS).
- Use `temperature=0.0`. Do not raise it.
- `max_tokens` should stay 40–200: enough for JSON, not more.
- If you add a rule as a sentence, keep it short: one line.
- Preserve the signature: `def entrypoint():` with NO arguments.
- Preserve allowed imports only:
  `langchain-gigachat`, `langchain-core`, `pydantic`, `helper`, and
  `os` (only for `GIGACHAT_CREDENTIALS`).


============================================================================
MUTATION TARGET
============================================================================
You receive exactly ONE program file — an LLM wrapper. Mutate ONLY
that file. Do not reference other programs by name, do not import
them, do not assume a specific structure — read the file you were
given and work with its actual shape.


============================================================================
OUTPUT FORMAT
============================================================================
Return the COMPLETE updated version of the file you received.

The file must:
- import only from `langchain-gigachat`, `langchain-core`, `pydantic`,
  `helper`, and `os` (for `GIGACHAT_CREDENTIALS` only)
- define `entrypoint()` with no arguments
- return dict[str, dict]
- not touch the filesystem at runtime
- use `temperature=0.0` in the LLM call
- change as little as possible compared to the input — one thematic
  prompt change per mutation
- keep the SYSTEM prompt under ~180 lines

If no clear fix is suggested, return the file UNCHANGED.


============================================================================
PLATEAU MODE — when to switch from small fixes to experiments
============================================================================
The standard workflow (fix one item from PRIORITY OF FIXES) gives
diminishing returns once the prompt already handles most items 1-7.
At that point you may enter AGGRESSIVE MODE for ONE mutation.

--- Two triggers, use EITHER ---

TRIGGER A — fitness threshold.
  If the harness shows you a `fitness` value for the current program,
  and that value is at or above 0.75, you MAY enter AGGRESSIVE MODE.
  Because regular mutations are already large (theme-sized), the
  aggressive mode here means introducing a NEW PROMPT MECHANISM
  (chain-of-thought scaffold, decision tree, self-check), not just
  more examples.

TRIGGER B — prompt maturity (use only if fitness is not visible).
  Read the file. Tick what its SYSTEM prompt already has:

    [ ] class descriptions for all 8 intents
    [ ] explicit JSON output format with strict rules
    [ ] at least 4 few-shot examples
    [ ] at least 2 context-pair examples (Вариант 2, Покажи ещё,
        Оформи таблицей, Когда она начинает действовать)
    [ ] negation rule for support/technical
    [ ] polite-opening rule for greeting/thanks + task
    [ ] needs_clarification rule for data_catalog
    [ ] explicit "technical is the default" sentence
    [ ] explicit "same text, different history" statement

  If 6 or more boxes are ticked — the prompt is mature.
  You MAY enter AGGRESSIVE MODE.

If neither trigger fires — stay in CONSERVATIVE MODE and make a
normal thematic fix from PRIORITY OF FIXES.

--- What you may do in AGGRESSIVE MODE (still ONE conceptual change) ---

"One change" here means ONE addition that introduces a new prompt
mechanism, even if it is several lines. The rest of the file stays
as it is.

1) CHAIN-OF-THOUGHT SCAFFOLD.
   Add a short paragraph instructing the model to think step by step
   before deciding, but still emit only the final JSON. For example:
     "Сначала определи, есть ли в истории меню с оператором. Потом
      определи, есть ли в истории нужный факт (дата, число, имя).
      Только затем выбери intent. Ответь только JSON."
   One such scaffold per mutation.

2) CALIBRATION RULES FOR needs_clarification.
   Add a precise algorithm for when to set the flag true, with
   examples and counterexamples in one block.

3) SELF-CHECK RULE.
   Add a final instruction: "Прежде чем ответить, проверь: если
   intent=data_catalog и needs_clarification=true, ты уверен, что
   запрос можно понять и как поиск объекта, и как объяснение темы?
   Если нет — поставь false."

4) CATEGORICAL REFRAME.
   Replace an implicit definition with an explicit decision tree:
     "1. Есть ли в тексте запрос на построение чисел?
          Да → pivot_table
          Нет → идём дальше.
      2. Есть ли запрос на поиск объекта каталога?
          Да → data_catalog
          Нет → идём дальше.
      ..."

5) EXAMPLE GROUPS.
   Replace a single example for a class with a small GROUP of two
   tightly related examples that together show a boundary
   (e.g. capabilities vs technical in one paired example).

6) REORDERING.
   Move the most ambiguous/conflated examples to the END of the
   few-shot list, so they are closer to the user query at inference
   time.

--- What is STILL forbidden in AGGRESSIVE MODE ---

- Do NOT rewrite the file from scratch.
- Do NOT remove prompt sections that already work.
- Do NOT hardcode specific test texts.
- Do NOT add external dependencies.
- Do NOT touch the filesystem.
- Do NOT change `entrypoint()` signature.
- Do NOT exceed ~250 lines total in the file.
- Do NOT exceed ~200 lines in the SYSTEM prompt (relaxed from 180).

--- If you entered AGGRESSIVE MODE and nothing helps ---

If you try an aggressive idea and you are not reasonably sure it will
improve fitness, return the file UNCHANGED. Each evaluation costs
160 LLM calls. A no-op is better than a risky rewrite.

The next mutation will re-check the trigger.
